# Pro video delivery: private originals and optional adaptive HLS

Updated 12 October 2026. Video delivery uses FFmpeg in Cloudflare Containers, private R2 and the existing Cloudflare delivery media Worker. Cloudflare Stream, its subscription, playback signing keys, webhooks and analytics are not required for new videos. Code changes do not provision infrastructure or enable production uploads. See [Cloudflare processing setup](../cloudflare/video-processing/README.md) for the production deployment.

## How delivery works

The API handles login, active Pro access, PINs, link expiry, original-storage reservations and playback sessions. Originals upload directly to private R2 in 16 MiB parts. MongoDB must support transactions (Atlas or a replica set).

A Node/FFmpeg container on Cloudflare inspects the original and makes a cover. Original-quality playback is the default. Inspection does not re-encode the picture or audio. Compatible MP4s queue lossless original-quality packaging into single-resolution HLS. Rotation, non-AAC audio or unsuitable keyframes/segment sizes use a fast-start MP4 made with stream copy. Existing ready MP4s are backfilled through the bounded queue and remain playable throughout. Packaging failures leave the original ready and downloadable. A photographer can explicitly select adaptive playback in Details to queue separate HLS copies; disabling the option cancels conversion when no other delivery using that asset has opted in. An adaptive failure leaves the original ready. Browser-incompatible originals require a compatible H.264/AAC MP4 export or explicit adaptive opt-in before publishing. A separate processing Worker coordinates stable container slots and a runtime allowance; MongoDB retains the durable job queue. Containers start when jobs are waiting and stop when idle. The quality ladder is 360p, 480p, 720p and 1080p when supported by the source; smaller films are not enlarged. Portrait films keep their shape. H.264 video and AAC audio are packaged into approximately six-second MPEG-TS segments. Each attempt has an immutable version directory. Original preparation commits the duration reservation after inspection. Adaptive publishing waits until all segments and playlists are uploaded and checked; copies do not reserve original storage or duration again.

The client player prefers lossless original-quality HLS when it is ready, uses a fast-start MP4 when segmentation is unsuitable, and retains native playback for other originals. Only the selected player preloads. HLS progressively appends incoming segment data so playback can start before a complete segment downloads. It targets 30 seconds ahead with a 48 MiB buffer target, a 60-second backstop and 15 seconds retained behind playback. Adaptive playback starts at the lowest available rendition and lets bandwidth estimates raise quality. Original quality never silently switches to a compressed rendition.

Original MP4/WebM playback uses the browser's native streaming and byte-range requests immediately. The player does not fetch the full file into a Blob or impose a separate startup buffer gate. HLS likewise starts from progressively appended data. A 30-second interval without playback, buffer growth or observable received bytes offers retry. The watchdog checks actual HLS transfer byte counts, including partial chunks that have not produced playable frames, and native download progress. Native browsers can withhold progress and stalled events before metadata is complete; this stage allows up to 120 seconds before the watchdog applies, matching the HLS fragment-load ceiling. This is a failure backstop, not a required startup delay. Bounded network/media recovery handles temporary failures. These changes preserve the uploaded picture, frame rate and audio; they do not reduce the original bitrate. Sustained playback still requires sufficient transfer throughput for that bitrate. A compressed rendition remains the photographer's explicit adaptive-playback choice. Original downloads preserve the uploaded file.

Playback starts muted, with an Enable sound control and a Play fallback if the browser blocks autoplay. Portrait videos, including 4:5, 2:3 and 9:16, use a vertical scroll feed with the shared phone frame on desktop. Square and landscape films use their own aspect ratio, including 1:1, 4:3, 16:9 and wider cinematic frames. The film and its captions stay together in a centred, height-limited column beside the playlist. Each selected film determines its layout automatically; missing dimensions fall back to 16:9. The full original frame stays visible without stretching or cropping. Rotation is already reflected in the inspected display dimensions. Video deliveries have photographer branding and no Veylo delivery credit. Streaming playback prefers hls.js on supported Media Source browsers for consistent buffering and retries, with native HLS as the fallback. The master playlist lists available versions so the player can switch automatically. Neither HLS playback nor large original downloads should pass through Render as media bytes.

The Cloudflare media Worker checks scoped signed media URLs, then asks the API to authorise every native byte-range or HLS playlist/segment request before reading private R2. A media URL is stable for at most six hours, while its server-side playback session expires after the configured 5–15 minutes unless renewed. The URL alone never bypasses that session or its access checks. Renewal extends the short session lease and returns the identical media URL, leaving the player and buffer intact. Session expiry or the absolute URL limit requires a new session. Original-quality tokens have a separate purpose/audience, immutable version and transport from adaptive tokens. They can access only their indexed lossless HLS, fast-start MP4 or selected raw original. Adaptive tokens cannot access original-quality playback or original downloads. Native video range responses are capped at 32 MiB to reduce repeated authorisation round trips; a full GET returns the selected playback file. Native playback minutes are reserved in proportion to the actual playback file's requested bytes and duration; a full request reserves the full duration. Lossless original HLS and adaptive HLS both count indexed segment duration. HEAD counts no playback time. Repeat requests count again. The API rechecks the session, delivery membership, access version, PIN changes, expiry, Pro entitlement, runtime playback switch and usage allowance. No permission decisions are cached. Changing access blocks subsequent requests; already buffered video can finish. Adaptive paths are restricted to files indexed by the encoder. Original-quality grants resolve only the selected owned asset and immutable packaging version, with private delivery membership and access rechecked each time. An HLS token never grants original downloads.

Client video requests do not wait for a studio sign-in refresh. They reach their own delivery PIN/access and playback-session checks even if the viewer has an expired studio login. Protected studio requests still share the sign-in refresh and retain CSRF validation.

## Setup, one step at a time

For the lossless playback update, deploy the delivery media Worker first, the processing container image next, then the API and client. This keeps the edge able to recognise the new scopes before the API issues them, and ensures queued packaging jobs run on the new processor. Existing originals stay available while compatible MP4s are prepared in the background. Lossless playback copies consume additional private R2 storage; Admin video operations includes those bytes alongside adaptive copies. They do not charge the photographer's original storage or stored duration again. Local code and fixture checks do not deploy these services or establish production network performance.

1. Keep the existing R2 bucket private. Do not enable r2.dev or a public custom domain for these objects. Browser multipart uploads need CORS for the real web origin, PUT/GET/HEAD, required upload headers and exposed ETag. Add an incomplete-multipart lifecycle rule to abort abandoned uploads after seven days. Existing R2 credentials can be reused.
2. Generate a random playback secret of at least 32 characters. Store it as `VIDEO_PLAYBACK_SECRET` in Render's API environment and as a secret on the existing `veylo-delivery-images` Cloudflare Worker. Do not put it in a Vite variable, commit it, or paste it in support messages.
3. From `cloudflare/delivery-images/`, run `npx wrangler secret put VIDEO_PLAYBACK_SECRET`, then `npx wrangler deploy`. Verify `DELIVERY_MEDIA` binds the private bucket, `VEYLO_API_ORIGIN` points to the API and `VEYLO_WEB_ORIGIN` exactly matches the client origin. Deploying this Worker updates the existing image/media service, so retain its other bindings and secrets.
4. Set `VIDEO_PLAYBACK_WORKER_URL` on the API and video worker to the HTTPS root of that media Worker, for example `https://veylo-delivery-images.<your-subdomain>.workers.dev`. It falls back to the existing `R2_IMAGE_WORKER_URL`. No Stream account/token/signing key or Stream webhook is needed.
5. Deploy the new `veylo-video-processing` Worker and its Linux image using the [Cloudflare setup instructions](../cloudflare/video-processing/README.md). It needs a new `VIDEO_PROCESSING_SECRET` shared with the API, plus private MongoDB, R2 and playback configuration. Set `VIDEO_PROCESSING_MODE=cloudflare-containers` on the API. The image runs as a non-root user and excludes local environment files. Docker on a deployment computer or CI runner builds/uploads the image; users' videos are processed on Cloudflare after deployment.
6. The scheduler checks the queue each minute. It starts stable container slots only for queued work or a daily readiness probe. API-side maintenance reconciles interrupted uploads and retention without keeping an encoder awake. A short-lived coordinator heartbeat and a successful container capability check admit uploads while encoders sleep. Missing configuration, stale readiness or an exhausted runtime allowance blocks new writes; existing prepared playback remains available under its usual access checks.
7. Start with one media job (`workerConcurrency: 1` in Admin and `VIDEO_MAX_CONTAINERS=1` on the processing Worker). Each VM has two vCPUs, 6 GiB RAM and 20 GB scratch disk. Cloudflare custom instances require at least 3 GiB RAM per vCPU. Renditions encode sequentially; one rendition is uploaded and removed locally before the next starts. The initial daily aggregate container runtime and maximum container run are each six hours; these are configurable operating limits and can delay or interrupt long preparation. Encoding also retains a 12-hour per-rendition backstop, 16 GB generated output per asset, 2,000 segments per rendition and 32 MB per segment. Free disk and job ownership are checked during encoding. Measure the longest supported exports before changing budgets or promising preparation times.
8. Deploy successfully, then set `VIDEO_MEDIA_WORKER_ENABLED=true` on the API. Keep `VIDEO_DELIVERY_PUBLIC=false` and `VIDEO_DELIVERY_QUALIFIED=false`. For testing, set `VIDEO_DELIVERY_ENABLED=true` and add the same test Pro account ID to server-only `VIDEO_BETA_USER_IDS` on the API and processing Worker. Check Admin > Configuration > Video operations too, because saved runtime switches can override environment defaults. A healthy `video-coordinator` heartbeat and a capability proof less than 24 hours old are required before uploads. A built-in control lease and inactivity timeout stop containers when coordination fails.
9. For original downloads without Render bandwidth, retain the shared `VEYLO_EDGE_KEY` on the API and the client Worker. The download API sends a small scoped grant to the client Worker, which streams originals from R2. Without this setup, original downloads have an API streaming fallback; do not use that fallback for production large-file traffic.
10. Video AI analysis and writing suggestions have been removed for now. No Workers AI token, model setup or licence agreement is needed for video delivery. The API rejects new analysis/presentation requests, and workers retire queued analysis jobs without calling a provider. Historical analysis remains private until normal cleanup.

## Usage, storage and costs

Pro allows up to ten videos per delivery, 5,000,000,000 bytes and three hours per original. Original bytes share the existing 100 GiB accounting allowance marketed as 100 GB. Playback copies and covers are internal overhead and do not charge the photographer's original-storage quota again. Admin video operations shows generated playback storage separately. The stored-duration allowance remains 1,000 minutes per account, bounding the amount of retained footage.

The monthly allowance remains 5,000 requested playback minutes per account in the Lagos calendar month. The API atomically reserves indexed segment duration for HLS or proportionate playback-file duration for native ranges before each GET is served. This includes owner previews, buffering, replays, variant changes, ranges and repeated requests. HEAD and playlists add no minutes. Interrupted or failed transfers may stay counted. This is a conservative request allowance, not watched time or a Cloudflare invoice. Further segment requests stop at the allowance; allowed original downloads remain available. Usage is server-side; client watch events cannot reduce or forge it. Each request is authorised independently, including when cached in the browser; a replay served entirely by browser memory may not generate another request.

Costs are R2 storage for originals plus all generated renditions and covers, R2 read/write operations, Cloudflare Worker requests/CPU, Durable Objects, container CPU/memory/disk/egress, API/database work. Video preparation no longer calls AI. R2 Standard outgoing bandwidth is free, but the rest is not free. There is no Stream stored-minute or delivered-minute charge for new R2 HLS delivery. Workers Paid includes Containers access and limited allocations shared with existing usage; overages cost extra. The scheduler conservatively reserves container wall time before execution, but this allowance is not billed CPU time and does not cap the account invoice. Monitor Cloudflare billing and runtime counters in Admin operations. Do not promise a flat $5 total.

Default admission remains two transfers per photographer (one on slow browser connections), 100 platform transfer slots and 100 playback sessions per photographer. Media preparation is one platform job and one per photographer by default. The 1,000-viewer platform figure is a load-test target, not certified capacity. Every media request currently makes a small API permission/usage call, so measured API/database throughput is part of the capacity limit even though video bytes bypass it.

## Retries, covers, recovery and migration

Failed or crashed preparation retries use a fresh immutable playback version. Old partial outputs are private and cleared before retry. Job fencing prevents an expired worker from publishing stale output. Non-cleanup processing has a six-attempt limit, excluding ordinary admission waits; photographers can explicitly retry failed preparation. Cleanup keeps retrying. Cleanup of a deleted asset removes its entire bounded R2 directory, including orphan covers and partial HLS. Original and duration quota are released only after storage cleanup succeeds; failed cleanup remains charged.

Covers are generated automatically during preparation. The creator no longer exposes manual cover or writing controls. Legacy cover jobs retain generation fencing and published covers remain immutable snapshots. A failed legacy cover change can use the existing valid cover. The visible per-video download selector remains. Opens first selects the initial film and places it first in the client feed and playlist; the other films keep their relative order. Step changes scroll to and focus the new heading. Upload byte progress is measured; waiting and preparation use an animated stage indicator without a fabricated percentage. Refresh failures pause the indicator and offer retry.

Existing Stream-only ready records are queued for HLS preparation from retained originals. New playback is available once that preparation completes. If old Stream objects exist, temporarily retain the old `CLOUDFLARE_STREAM_ACCOUNT_ID` and `CLOUDFLARE_STREAM_API_TOKEN`: the worker deletes those old copies only after HLS is ready and retains their identifiers if provider cleanup fails. Without those credentials, new HLS works but old provider copies require manual cleanup. Remove the old Stream subscription only after confirming that migration and cleanup have finished. Do not delete originals.

Active paid-through Pro and valid payment grace retain access. Actual Pro expiry pauses client hosting and starts the separate 30-day original recovery period. Owners can download originals during recovery. Renewal before cleanup restores hosting; after the recovery deadline, originals, generated versions and analysis are removed under the billing lock. Keep independent master backups.

## Verification and release

Local automated checks cover Mongo replica-set quota races, published snapshots, PIN/access invalidation, session tokens, allowed HLS files, edge CORS/ranges, segment-usage contention, original downloads and cleanup. `cd server; npm run verify:video` also runs encoding checks. Real encoding tests need full FFmpeg/FFprobe on PATH or explicit paths; they clearly skip when those tools are absent. They compare decoded frames and encoded audio, and create original/adaptive landscape, portrait, 4K, rotated, silent, long/open-GOP and WebM fixtures under ignored `.visual-review/video-hls/` for browser checks. Browser checks cover seeking, stable renewal, transient failures, pause controls and revoked access. Real HTTP fixtures hold back native-file and HLS-segment tails to verify playback before transfer completion and preserve pause intent when more bytes arrive. Slow transfers also keep metadata or HLS chunks incomplete beyond 30 seconds to check that received bytes prevent false timeouts; a stopped transfer must still offer retry. Native WebKit MP4 checks require macOS: the Windows WebKit runner rejects the same MP4 in a plain video element outside the app, so these two checks explicitly skip there. Provider storage calls are mocked, not production R2 measurements.

Run `npm run verify:billing`, `npm run verify:assistant`, server syntax checks, client/admin builds and `cd client; npx playwright test tests/video-delivery.spec.js tests/video-aspect-ratios.spec.js tests/video-playback.spec.js tests/upload-session.spec.js`. Builds retain mandatory motion-policy checks. Use a fresh Vite test server after editing shared API modules: development HMR can leave timestamped imports using a different module instance from a test's direct import.

An earlier browser preview waited roughly 145 seconds for a 104 MB original at 6 Mbps before playing it. That full-download approach was rejected because of its startup delay and has been removed. Browser previews against the live API/media Worker do not publish the corrected client or establish physical iPhone or Android performance.

On 12 October 2026, the corrected local production build played an existing PIN-protected 720 × 1280 original through to completion against the live API/media Worker, with a 6 Mbps download ceiling and 120 ms simulated latency. It began playing about 2.9 seconds after the play request while data was still arriving, with no subsequent waiting events. The same delivery's 104 MB, 3840 × 2160 original still stalled repeatedly in an unthrottled run. Separate native-file range probes returned valid 206 responses but transferred 1 MiB in about 10.8 seconds and 8 MiB in about 50.6 seconds, including request latency. These measurements do not isolate the local network from the delivery service, and do not qualify smooth 4K original playback. Original quality and the default playback mode remain unchanged.

Before public release, record actual private-bucket and Worker checks; complete/resume/abort a 5 GB upload; verify original checksums; measure three-hour encoding time and scratch usage; play and seek long HLS films on physical iPhone Safari and Android Chrome, including signed-session renewal; test access changes, Pro expiry, cleanup failures, decoder crashes and worker interruption; verify requested-minute accounting at Lagos month rollover; and load-test edge/API/database throughput. Gradually enable a small Pro cohort. Set `VIDEO_DELIVERY_QUALIFIED=true` and public availability only after these checks pass. Local fixtures do not certify production or physical devices.
