# Pro video delivery: private R2 adaptive HLS

Updated 11 October 2026. Video delivery now uses FFmpeg, private R2 and the existing Cloudflare delivery media Worker. Cloudflare Stream, its subscription, playback signing keys, webhooks and analytics are not required for new videos. The separate video worker still needs a machine to run on. Code changes do not provision infrastructure or enable production uploads.

## How delivery works

The API handles login, active Pro access, PINs, link expiry, original-storage reservations and playback sessions. Originals upload directly to private R2 in 16 MiB parts. MongoDB must support transactions (Atlas or a replica set).

A separate Node/FFmpeg worker inspects the original, makes a cover, and encodes adaptive HLS. The quality ladder is 360p, 480p, 720p and 1080p when supported by the source; smaller films are not enlarged. Portrait films keep their shape. H.264 video and AAC audio are packaged into approximately six-second MPEG-TS segments. Each attempt has an immutable version directory. Nothing becomes playable until all segments and playlists are uploaded, checked, and committed with the duration reservation.

The existing client player uses native HLS where supported and hls.js elsewhere. The master playlist lists available versions so the player can switch automatically. Original downloads preserve the uploaded file. Neither HLS playback nor large original downloads should pass through Render as media bytes.

The Cloudflare media Worker checks short-lived signed playback tokens, then asks the API to authorise every playlist/segment request before reading private R2. The API rechecks the session, delivery membership, access version, PIN changes, expiry, Pro entitlement, runtime playback switch and usage allowance. No permission decisions are cached. Changing access blocks subsequent requests; already buffered video can finish. Paths are restricted to files indexed by the encoder. An HLS token never grants original downloads.

## Setup, one step at a time

1. Keep the existing R2 bucket private. Do not enable r2.dev or a public custom domain for these objects. Browser multipart uploads need CORS for the real web origin, PUT/GET/HEAD, required upload headers and exposed ETag. Add an incomplete-multipart lifecycle rule to abort abandoned uploads after seven days. Existing R2 credentials can be reused.
2. Generate a random playback secret of at least 32 characters. Store it as `VIDEO_PLAYBACK_SECRET` in Render's API environment and as a secret on the existing `veylo-delivery-images` Cloudflare Worker. Do not put it in a Vite variable, commit it, or paste it in support messages.
3. From `cloudflare/delivery-images/`, run `npx wrangler secret put VIDEO_PLAYBACK_SECRET`, then `npx wrangler deploy`. Verify `DELIVERY_MEDIA` binds the private bucket, `VEYLO_API_ORIGIN` points to the API and `VEYLO_WEB_ORIGIN` exactly matches the client origin. Deploying this Worker updates the existing image/media service, so retain its other bindings and secrets.
4. Set `VIDEO_PLAYBACK_WORKER_URL` on the API and video worker to the HTTPS root of that media Worker, for example `https://veylo-delivery-images.<your-subdomain>.workers.dev`. It falls back to the existing `R2_IMAGE_WORKER_URL`. No Stream account/token/signing key or Stream webhook is needed.
5. Run the dedicated video worker. For Docker, from `server/`, build `docker build -f VideoDelivery.Dockerfile -t veylo-video-worker .`. Alternatively install full FFmpeg/FFprobe and run `npm run video:worker` from `server/`. Supply the same MongoDB, R2, playback, entitlement/billing, email and runtime settings as the API. The Docker image runs as a non-root user and excludes local environment files. A Render background worker or another reliable host can run it; this hosting is separate from the $5 Workers subscription.
6. For a small pilot, the Node worker can run on your own computer. It must remain on, connected and running while jobs are processed. Use a private server environment file and full FFmpeg/FFprobe; optional `FFMPEG_PATH` and `FFPROBE_PATH` point to the binaries. Sleeping or stopping that machine pauses preparation, though already prepared films remain hosted. This is not a production availability guarantee.
7. Start with one media job (`workerConcurrency: 1`, also checked in Admin configuration), at least 15 GB of free temporary disk, and measured CPU/RAM limits. Renditions encode sequentially; one rendition is uploaded and removed locally before the next starts. Encoding is capped at 12 hours per rendition, 16 GB generated output per asset, 2,000 segments per rendition and 32 MB per segment. Free disk and job ownership are checked during encoding. Raising concurrency requires proportionally more resources. Long films can take hours on a small CPU; measure real preparation times.
8. Start the worker successfully, then set `VIDEO_MEDIA_WORKER_ENABLED=true` on the API and worker. Keep `VIDEO_DELIVERY_PUBLIC=false` and `VIDEO_DELIVERY_QUALIFIED=false`. For testing, set `VIDEO_DELIVERY_ENABLED=true` and add the test Pro account ID to server-only `VIDEO_BETA_USER_IDS`. Check Admin > Configuration > Video operations too, because saved runtime switches can override environment defaults. A recent healthy worker heartbeat is required before writes are accepted.
9. For original downloads without Render bandwidth, retain the shared `VEYLO_EDGE_KEY` on the API and the client Worker. The download API sends a small scoped grant to the client Worker, which streams originals from R2. Without this setup, original downloads have an API streaming fallback; do not use that fallback for production large-file traffic.
10. AI is optional and unchanged. Configure the listed Workers AI models and private credentials, complete any required model licences, then set `VIDEO_AI_MODEL_READY=true`. Manual writing works without AI.

## Usage, storage and costs

Pro allows up to ten videos per delivery, 5,000,000,000 bytes and three hours per original. Original bytes share the existing 100 GiB accounting allowance marketed as 100 GB. Playback copies and covers are internal overhead and do not charge the photographer's original-storage quota again. Admin video operations shows generated playback storage separately. The stored-duration allowance remains 1,000 minutes per account, bounding the amount of retained footage.

The monthly allowance remains 5,000 requested playback minutes per account in the Lagos calendar month. The API atomically reserves the full indexed segment duration before each GET is served. This includes owner previews, buffering, replays, variant changes, ranges and repeated requests. HEAD and playlists add no minutes. Interrupted or failed transfers may stay counted. This is a conservative request allowance, not watched time or a Cloudflare invoice. Further segment requests stop at the allowance; allowed original downloads remain available. Usage is server-side; client watch events cannot reduce or forge it. Each request is authorised independently, including when cached in the browser; a replay served entirely by browser memory may not generate another request.

Costs are R2 storage for originals plus all generated renditions and covers, R2 read/write operations, Cloudflare Worker requests/CPU, API/database work for permission and usage checks, encoding-machine hosting, and optional AI. R2 Standard outgoing bandwidth is free, but the rest is not free. There is no Stream stored-minute or delivered-minute charge for new R2 HLS delivery. Monthly free allocations are shared with all existing account usage. Monitor Cloudflare billing and worker CPU/RAM/disk alongside Admin operations. Do not promise that the current $5 Workers subscription covers encoding hosting.

Default admission remains two transfers per photographer (one on slow browser connections), 100 platform transfer slots and 100 playback sessions per photographer. Media preparation is one platform job and one per photographer by default. The 1,000-viewer platform figure is a load-test target, not certified capacity. Every media request currently makes a small API permission/usage call, so measured API/database throughput is part of the capacity limit even though video bytes bypass it.

## Retries, covers, recovery and migration

Failed or crashed preparation retries use a fresh immutable HLS version. Old partial outputs are private and cleared before retry. Job fencing prevents an expired worker from publishing stale output. Cleanup of a deleted asset removes its entire bounded R2 directory, including orphan covers and partial HLS. Original and duration quota are released only after storage cleanup succeeds; failures remain retryable and charged.

Choosing a cover frame now queues a background FFmpeg job. The creator shows preparation/failure and refreshes when ready. A custom cover upload remains immediate. Generation IDs keep an older frame job from overwriting a newer choice. Published covers remain immutable snapshots; wait for cover preparation before publishing.

Existing Stream-only ready records are queued for HLS preparation from retained originals. New playback is available once that preparation completes. If old Stream objects exist, temporarily retain the old `CLOUDFLARE_STREAM_ACCOUNT_ID` and `CLOUDFLARE_STREAM_API_TOKEN`: the worker deletes those old copies only after HLS is ready and retains their identifiers if provider cleanup fails. Without those credentials, new HLS works but old provider copies require manual cleanup. Remove the old Stream subscription only after confirming that migration and cleanup have finished. Do not delete originals.

Active paid-through Pro and valid payment grace retain access. Actual Pro expiry pauses client hosting and starts the separate 30-day original recovery period. Owners can download originals during recovery. Renewal before cleanup restores hosting; after the recovery deadline, originals, generated versions and analysis are removed under the billing lock. Keep independent master backups.

## Verification and release

Local automated checks cover Mongo replica-set quota races, published snapshots, PIN/access invalidation, session tokens, allowed HLS files, edge CORS/ranges, segment-usage contention, original downloads and cleanup. `cd server; npm run verify:video` also runs encoding checks. Real encoding tests need full FFmpeg/FFprobe on PATH or explicit paths; they clearly skip when those tools are absent. They create landscape/portrait fixtures under ignored `.visual-review/video-hls/` for browser checks. Provider storage calls are mocked, not production R2 measurements.

Run `npm run verify:billing`, `npm run verify:assistant`, server syntax checks, client/admin builds and `cd client; npx playwright test tests/video-delivery.spec.js`. Builds retain mandatory motion-policy checks.

Before public release, record actual private-bucket and Worker checks; complete/resume/abort a 5 GB upload; verify original checksums; measure three-hour encoding time and scratch usage; play and seek long HLS films on physical iPhone Safari and Android Chrome, including signed-session renewal; test access changes, Pro expiry, cleanup failures, decoder crashes and worker interruption; verify requested-minute accounting at Lagos month rollover; and load-test edge/API/database throughput. Gradually enable a small Pro cohort. Set `VIDEO_DELIVERY_QUALIFIED=true` and public availability only after these checks pass. Local fixtures do not certify production or physical devices.
